# TripGo — ЛР2

HTTP-сервис поездок с PostgreSQL, миграциями goose, контекстным менеджером транзакций и телеметрией OpenTelemetry.

| Метод | Путь                            | Назначение                                |
| ----- | ------------------------------- | ----------------------------------------- |
| POST  | `/api/v1/trips`                 | Создать поездку                           |
| GET   | `/api/v1/trips/{tripId}`        | Получить поездку                          |
| POST  | `/api/v1/trips/{tripId}/finish` | Завершить поездку                         |
| GET   | `/health`                       | Проверить, что процесс работает           |
| GET   | `/ready`                        | Проверить доступность БД: `200` или `503` |

## Запуск

Требования: Go 1.26.3 или новее, Docker, `tripgoctl`, `make`.
Команды выполняются из корня репозитория.

```sh
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

`tripgoctl` создаёт `.env` с адресами компонентов текущего окружения.
`make run` загружает значения из `.env.example`, затем из `.env` и сохраняет
приоритет переменных, уже экспортированных в окружении. Дописывать настройки
в сгенерированный `.env` не нужно.

```sh
make migrate
make run
```

При запуске выполняется `Ping` БД; без доступного PostgreSQL сервис не стартует.
Для остановки сервиса нажмите `Ctrl+C`. По `SIGINT` или `SIGTERM` сервер
дожидается текущих запросов, завершает экспорт телеметрии и закрывает пул БД
в пределах `SHUTDOWN_TIMEOUT`. Окружение останавливается отдельно:
`tripgoctl environment stop`.

## Переменные окружения

Go-программа читает переменные окружения. Загрузку файлов выполняет Makefile.
При запуске через `make run` приоритет такой: окружение → `.env` → `.env.example`.
Миграции и интеграционные тесты берут `DATABASE_URL` из окружения или `.env`,
причём окружение имеет приоритет. При прямом запуске бинарного файла все
настройки нужно передать через окружение.

| Переменная                    | Значение из `.env.example`                              | Назначение                             |
| ----------------------------- | ------------------------------------------------------- | -------------------------------------- |
| `HTTP_ADDR`                   | `:8080`                                                 | Адрес HTTP-сервера                     |
| `HTTP_READ_TIMEOUT`           | `15s`                                                   | Таймаут чтения запроса                 |
| `HTTP_READ_HEADER_TIMEOUT`    | `5s`                                                    | Таймаут чтения заголовков              |
| `HTTP_WRITE_TIMEOUT`          | `15s`                                                   | Таймаут записи ответа                  |
| `HTTP_IDLE_TIMEOUT`           | `60s`                                                   | Таймаут простоя соединения             |
| `LOG_LEVEL`                   | `info`                                                  | Уровень логирования                    |
| `SHUTDOWN_TIMEOUT`            | `10s`                                                   | Общий бюджет остановки                 |
| `DATABASE_URL`                | Из `.env`, созданного `tripgoctl`                       | Адрес и параметры подключения к БД     |
| `DATABASE_MAX_CONNS`          | `10`                                                    | Максимум соединений пула               |
| `DATABASE_MIN_CONNS`          | `2`                                                     | Минимум соединений пула                |
| `DATABASE_MAX_CONN_LIFETIME`  | `30m`                                                   | Максимальное время жизни соединения    |
| `DATABASE_CONNECT_TIMEOUT`    | `5s`                                                    | Таймаут подключения к БД               |
| `DATABASE_QUERY_TIMEOUT`      | `3s`                                                    | Таймаут запросов и транзакций          |
| `OTEL_SERVICE_NAME`           | `trip-service`                                          | Имя сервиса в телеметрии               |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Из `.env`, созданного `tripgoctl`                       | Адрес коллектора                       |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf`                                         | Протокол экспорта трейсов и метрик     |
| `OTEL_RESOURCE_ATTRIBUTES`    | `service.namespace=tripgo,deployment.environment=local` | Атрибуты ресурса                       |
| `OTEL_TRACES_SAMPLER`         | `parentbased_always_on`                                 | Правило сэмплирования трейсов          |
| `OTEL_EXPORTER_OTLP_TIMEOUT`  | `3000`                                                  | Таймаут экспорта, миллисекунды         |
| `OTEL_METRIC_EXPORT_INTERVAL` | `5000`                                                  | Интервал экспорта метрик, миллисекунды |
| `OTEL_METRIC_EXPORT_TIMEOUT`  | `5000`                                                  | Таймаут экспорта метрик, миллисекунды  |

`service.version` определяется по метаданным Go-сборки. Переменные следующих
лабораторных из `.env.example` пока не используются.

## Проверка и генерация

```sh
make build
make lint
make test
make generate
make migrate-validate
make migrate-status
```

`make test` запускает unit-тесты с `-race -count=2`, измеряет покрытие
`internal/domain/...` и `internal/usecase/...` и печатает итог в строке `total`.
По условию итоговое покрытие этих пакетов должно быть не ниже 50%.
Профиль покрытия хранится во временном файле и удаляется после команды.

Для интеграционных тестов нужен PostgreSQL текущего окружения с применёнными
миграциями:

```sh
tripgoctl environment start
make migrate
make test-integration
```

`make test-integration` запускает тесты репозиториев с тегом `integration`
и флагами `-race -count=2`. Каждый тест создаёт записи со случайными UUID
и удаляет свои данные. Проверяются операции репозиториев, конкурентное
завершение, сохранение поездки с историей и полный откат при ошибке.
Обычный `make test` не требует запущенной БД.

Для обновления только моков выполните:

```sh
go generate ./internal/usecase/... ./internal/http/...
```

Команды `go:generate` находятся в `contract.go`. `mockgen` записывает моки
в соседние `mocks_test.go`; эти файлы хранятся в репозитории.

`make generate` воспроизводит типы и серверные интерфейсы пяти операций из OpenAPI,
затем обновляет все моки.
`make migrate-down` откатывает одну миграцию; `make migrate` применяет недостающие.

## Архитектура

| Пакет                                       | Назначение                                                    |
| ------------------------------------------- | ------------------------------------------------------------- |
| `cmd/trip-service`                          | Читает конфигурацию, настраивает логгер и запускает контейнер |
| `internal/container`                        | Создаёт и связывает зависимости, управляет остановкой         |
| `internal/domain/trip`                      | Модель поездки, валидация, переход `Finish` и доменные ошибки |
| `internal/usecase/trip/{create,get,finish}` | Сценарии работы с поездкой через интерфейсы зависимостей      |
| `internal/http`                             | Роутер, middleware и отдельный пакет для каждой ручки         |
| `internal/http/domainerror`                 | Единый перевод доменных ошибок в `Problem`                    |
| `internal/repository`                       | SQL-запросы и преобразование данных PostgreSQL                |
| `internal/infra`                            | Пул БД, менеджер транзакций, OpenTelemetry и обработчик slog  |
| `internal/generated`                        | Типы и интерфейс HTTP-сервера из OpenAPI                      |

Домен не знает про инфраструктуру. Юзкейсы используют домен и интерфейсы,
объявленные в своих `contract.go`. Хендлеры объявляют интерфейсы нужных им
юзкейсов; репозитории объявляют интерфейсы исполнителя SQL. Ограничения импортов
проверяет `depguard` в `make lint`.

Отдельного пакета `model` нет: между слоями передаётся доменная `Trip`,
а вход создания описан типом `create.Input`. Менеджер транзакций находится
непосредственно в `infra/postgres`, инициализация SDK — в
`infra/postgres/telemetry`, бизнес-метрики — в `infra/telemetry/tripmetrics`.
Отдельная модель для передачи данных сейчас не нужна: доменная `Trip` содержит
данные всех трёх сценариев. Пул и менеджер транзакций объединены работой с pgx.
При таком расположении инфраструктурных пакетов границы слоёв сохраняются:
пакеты создаются контейнером, домен и юзкейсы их не импортируют.
Код собирается вручную, без DI-фреймворка.

Основные решения:

- Изоляция — `Read Committed`: запрет двух активных поездок обеспечивает уникальный
  индекс, а завершение проверяет статус в самом `UPDATE`; более строгий уровень для этих операций не нужен.
- `TxManager.Do` открывает транзакцию и сохраняет её в контексте. Репозитории выбирают
  транзакцию из контекста или пул. Успех приводит к `COMMIT`, ошибка или паника — к `ROLLBACK`;
  паника пробрасывается наружу. Вложенный `Do` использует ту же транзакцию.
- Создание и завершение записывают поездку и историю статусов в одной транзакции.
  SQL строится `squirrel` с параметрами `$N`; работа с БД выполняется через `pgxpool`.
- Частичный уникальный индекс `trips_active_driver_idx` по `driver_id` для `status = 'active'`
  защищает от конкурентного создания. Его нарушение преобразуется в `409 driver_busy`.
- Юзкейс читает поездку, вызывает доменный `Finish`, затем в транзакции сохраняет
  поездку и историю. Завершение использует `UPDATE ... WHERE id = $1 AND status = 'active'`.
  Дополнительное чтение отличает отсутствующую поездку (`404`) от завершённой (`409`).

## Проверка наблюдаемости

Запустите сервис через `make run`. Адреса Jaeger, Grafana и Prometheus возьмите
из `tripgoctl connect`.

Создайте поездку, затем получите и завершите её:

```sh
curl -i -X POST http://localhost:8080/api/v1/trips \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"11111111-1111-4111-8111-111111111111","driver_id":"22222222-2222-4222-8222-222222222222","start_point":{"latitude":55.75,"longitude":37.62},"end_point":{"latitude":55.8,"longitude":37.7},"price":500}'

trip_id='<id из ответа на создание>'
curl -i "http://localhost:8080/api/v1/trips/$trip_id"
curl -i -X POST "http://localhost:8080/api/v1/trips/$trip_id/finish"
```

HTTP-адрес в примере соответствует `HTTP_ADDR=:8080` из `.env.example`.
При повторном создании с тем же водителем завершите его предыдущую поездку,
иначе получите `409 driver_busy`.

1. В JSON-логе найдите запись `request handled` и скопируйте `trace_id`.
2. В Jaeger найдите этот трейс. Внутри HTTP-спана видны спан юзкейса и обращения к БД.
3. В Grafana откройте Explore и выберите источник Prometheus. Проверьте метрики
   `http_server_request_duration_seconds_count`, `db_client_operation_duration_seconds_count`,
   `tripgo_trips_created_total` и `tripgo_trips_completed_total`.
4. Проверьте, что `http_route` содержит шаблон `/api/v1/trips/{tripId}`, а не UUID поездки.
5. Для проверки недоступности коллектора остановите сервис и запустите его
   с `OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:1 make run`.
   Запросы должны продолжать выполняться. Ошибки экспорта записываются
   переданным логгером в stdout в JSON на уровне `Warn`.
   После проверки остановите сервис и верните обычный `make run`.

Middleware подключены в порядке `Recover → Tracing → Logging → Metrics → роутер`.
Логи пишутся в stdout в JSON. Записи внутри спанов содержат `trace_id` и `span_id`.
Трейсы и метрики уходят по OTLP в коллектор. Скриншоты трейса из Jaeger и метрик
из Grafana приложите к PR.
